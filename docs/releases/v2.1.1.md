# Buddy2api v2.1.1

发布日期：2026-08-27

TraeWork 延迟优化：流式提前转发思考文本 + 网关开销削减。

## 变更

- **流式提前转发**：traework 流式请求立即返回首包（TTFB ~0.1s，原先要等整轮跑完才有第一个字节）；上游 agent 产生规划/思考文本（plan_item 的 thought/reasoning_content）时提前分段转发为 content chunk，回合结束后补发完整回答（答案已包含在已转发文本里则不重发）。上游累计重发的思考只转发增量，客户端不会看到重复段。
- **网关开销削减**：回合内固定等待 350ms → 100ms；会话删除与连接关闭移到后台执行，不阻塞响应（每请求省 ~0.3-0.5s）。
- 流式中途失败时，在流内补一条失败说明后正常收尾（`finish_reason: stop` + `[DONE]`）。旧行为是流开始前就以 JSON 错误返回；现在流先返回、回合后台跑，错误可能发生在流中途，需要流内表达。
- 非流式行为不变。

## 实测（pong 请求）

| 指标 | 改前 | 改后 |
|---|---|---|
| 流式首包（TTFB） | ~12-16s（整块一次性下发） | ~0.1s |
| 首个可见内容 | ~12-16s | ~6-10s（取决于上游 agent 何时产生思考） |
| 总时长 | ~13-16s | ~14s（上游 agent 执行主导，基本不变） |

慢的主因在上游：每次请求在云端沙箱跑一整轮 SOLO agent（纯 LLM 推理仅 ~1-2s，其余是 agent 脚手架、沙箱与多次 LLM pass），网关层无法绕开。延迟敏感场景建议走 workbuddy 通道。
